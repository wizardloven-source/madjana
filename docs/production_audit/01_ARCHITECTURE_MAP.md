## 6. Key Architectural Observations

### Strengths
- Clean separation between packages (core → data → apps)
- All SQLite access isolated in DAOs under `data/lib/src/datasources/local/`
- All Supabase access isolated in remote datasources under `data/lib/src/datasources/remote/`
- Repository interfaces defined in core, implementations in data
- Use cases exist for critical write paths (egg, mortality, feed, medication, dispatch)
- Offline-first: all writes go to SQLite first, queued for sync
- No raw SQL in Flutter app layer

### Weaknesses
- **Domain package is empty** — adds no architectural value
- **Multiple layering violations** — widgets/providers calling Supabase directly
- **No use-case layer for reads** — all read paths bypass use cases
- **No use cases for payments, customers, expenses, inventory**
- **Two apps have different feature sets** — mobile lacks expenses/inventory/approvals/onboarding; desktop lacks notes/reminders/emergency
- **Provider graph is split** — mobile `providers.dart` and desktop `providers.dart` are separate, not shared
- **No navigation/routing abstraction** — mobile uses named routes, desktop uses role-based shell
